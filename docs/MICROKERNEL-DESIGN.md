# 生成式 AIOS × GeoOS 微内核设计草案

状态：**设计提案，未实现**。逆向评审后的规范化补充见 [微内核最小契约 r1](MICROKERNEL-CONTRACT.md)，委托链、派生数据及跨attempt上下文、执行许可、回执和取消语义以该文为准。v0.17及以前是实验材料，不是本设计的实现声明。本文在双 BP 原始证据与用户后续澄清之间区分来源；不能把愿景当作已具备的认知、地理或设备能力。

## 1. 先确定系统是什么

用户打开的不是一个固定聊天页，也不是若干业务 App 的集合，而是自己的 AI 生物所在的、与当下生活有关的场景。生物像有个性的伙伴，能听、看、交流、与用户和其他主体维持关系；按需求和情境寻找、调用或生成服务，并产生合适的交互场景。用户可以拥有多个生物，每个可以作为独立 Agent 运行，个性、能力、关系和记忆边界不同。模型只是后台支持，并不等于生物身份。

GeoOS 不是随后加上去的地图：它组织固定/移动主体、方向性地理通信、区域内容与服务环境，提供“周围有什么、谁可以感知谁、谁可以向哪里发布”的基础关系。AIOS 使生活于这一环境的主体能够理解和回应。地理入口、业务入口、用户入口是同一个持续情境的不同进入方式，不是三个按钮或三套账号。

“上班”是具体检验：在用户允许使用的证据和习惯基础上，生物可提前提出/准备工作场景。打开 App 即进入这个场景，而非先打开聊天框再选功能。识别不确定时保留可纠正的建议，不把预测当事实；纠正不会销毁未完成工作，也不能默认连续追踪用户行踪。

## 2. 证据、澄清、工程选择

| 层次 | 内容 |
|---|---|
| AIWatch BP p3–4 | 多模态感知、AIBM四边界、指令调度、连接、渲染与服务；服务直接组织，不以App为基本架构；AI可按需调用或生成服务 |
| AIWatch BP p6–8 | 菜品图片放大跨端；猫的形象/真人隐私分离；工厂持续主体与广播；要求文字后才生成窗口；空调不可达时改提醒；汽车保存拒绝付费并稍后指导 |
| AIWatch BP p9 | 固定/移动AI生物、地理感知与商业连接 |
| GeoChat BP角色定义 | Geomotion移动收发，AReality固定收发，Broadcast固定只发，地理群只感知；区域内容/空间组织不等于UI地图 |
| 用户最新澄清 | 生成式OS；伙伴式有个性生物；多Agent；三类入口；按习惯提前准备场景；先微内核再扩展 |
| 以下工程提案 | 安全主体、因果事件、能力租约、连续情境、持久活动、场景声明等机制；不是BP原文已有技术实现 |

不把“生物”当生命/意识的已证实声明，也不把用户对产品自然感的要求降格为一个服务ID或头像。

## 3. 什么必须稳定，什么应当生成

**稳定的是：** 生物身份与归属、人格版本与关系连续性、用户约定与拒绝、权限、事实来源、未完成工作、真实结果。更换模型、设备或界面不能让这些丢失或扩大权限。

**变化的是：** 对当下情境的解释候选、响应方式、服务方案、临时能力组合、交互结构、具体呈现。旧界面收起不是生物死亡，也不是任务取消；新界面不能创造新的所有者或授权。

人格与关系是生物的持续契约，不是内核里的语言模型算法：内核保护人格/关系引用及其版本、归属和读写范围；人格表达、记忆检索、习惯学习、情绪表现由可替换的生物Agent运行时完成。必须能在换模型后仍是同一个伙伴，且不同生物不会偷读彼此私有记忆。用户对某个生物的关系不等同于生物获得用户全部权限。

## 4. 微内核边界候选：五组必须保护的机制

这是**应用层运行微内核**，先运行在普通服务端与Flutter承载端之上；不是宣称已替代Android/Linux硬件内核。

### K1 主体、关系与连续身份

维护 `BeingId / PrincipalId / RelationId` 和生命周期，绑定受保护的 `personaRef@version`、`memoryNamespace`、AIBM边界引用及可选GeoFacet。用户、生物、业务主体、设备是不同角色；一个用户可有多个生物；生物不能冒充真人。

关系对象至少含两端身份、关系种类、可见范围、数据共享范围、版本和来源；“好友/伙伴/代理”文字本身不授予权限。人格/记忆正文不进入小内核，关系语义推理也不进入，但持续引用、隔离与变更证据必须受内核保护。

### K2 可撤销能力与边界判断

每次活动都计算边界交集，而非让模型决定权限：调用者授权 ∩ 生物能力 ∩ 地理方向/作用范围 ∩ 区域政策 ∩ 当前连接可达性 ∩ 数据用途/接收方 ∩ 用户明确约束。

能力凭据绑定谁、对谁、做什么、作用域、效果类别、有效期/版本、授权来源；默认无权。单次授权与持续授权分开。任何一层撤销都递增相应世代；排队获准不等于稍后仍可执行：实际dispatch前重新校验版本、连接和全部约束，返回时再校验结果的接纳/披露边界。读取和真实执行也分别授权，发现候选不执行。

### K3 事件来源、因果与持续情境

统一接纳被认证适配器产生的证据，保留来源、时间、模拟/实测标记、质量与因果链。音频转写/图像文字是观察结果，不是已授权命令；模型提出的是解释候选，不是可信事件来源。认证传感器只能证明数据来自该设备，不能证明说话者就是所有者；必须另有会话/注意对象/用户表达归因证据，电视声、邻人的指令和屏幕文字不能直接变为用户授权。

`ContinuityId` 连接同一段生活/业务情境的用户、生物、关系、证据、意图、约束、任务和呈现引用。三个入口只改变起点，不改身份及约束。多个生物可在被允许的同一情境协作，每个仍保留独立边界。

内核保护情境版本和成员访问，不负责推断“现在上班了”。该推断由情境服务提交可纠正提案，带证据引用、置信度和有效期；用户纠正形成新证据，而非静默改写事实。

### K4 受控活动与可靠回执

可持久恢复的活动记录承载即时服务、未来任务及生成工作流。用户意图状态与执行事实状态独立，取消请求不能覆盖已发生效果；具体双状态、派发许可和成功判据以最小契约第4–6节为准。等待用户/证据/暂停也须明确，不用“处理中”掩盖未知。

每个活动引用确定版本的服务清单与输入、约束、权限世代、幂等键、触发条件和回执。跨进程外部动作不许仅凭发出请求就记为成功；连接断开时可成为uncertain，并查询/核对，不能盲目重发。撤权禁止继续执行或越权披露，但不能抹掉已经发生的外部事实：迟到回执应保存为受保护的事实/待核对状态，不能假装动作未发生；呈现该事实与再次行动仍分别检查权限。生成服务需要独立验证及授权后才成为可运行清单。

### K5 资源生命期与交付绑定

把Agent运行、能力连接、感知采集、任务执行及呈现承载作为有配额、可取消、可回收的资源。内核保护 `ContinuityId ↔ SceneId ↔ DeviceLease` 的绑定、版本和撤销，不运行UI布局或图片生成算法。

场景显示/更新/移到另一设备/收起只改变呈现租约，不重复下单、不复制生物、不丢任务。用户明确停止生物/任务是另外的指令。生物Agent可以离开前台继续授权活动；但后台设备感知受平台权限与实际存活能力限制，不由“持续生物”推导永远监听。

**为何保护这些机制，而不是吞下整个生态：** 没有K1不是同一个伙伴；没有K2生成会变成扩权；没有K3场景更换就丢因果或把观察当命令；没有K4离开前台就失去工作且无法核实完成；没有K5跨端/后台不能可靠回收与延续。其余算法可在这些契约之外替换。这里证明的是产品运行需要这些不变量，不是证明所有对象必须写进内核。最终内核分工须由最小反例确定：先用身份、版本化资源、能力、事件与活动保护这些不变量，再判断是否需要专门的情境/场景对象。

## 5. 明确不放进微内核

- ASR、图像/空间理解、声学模型、LLM与Agent推理策略。
- 个性表达、动画/语音合成、情感风格、记忆摘要和习惯预测。
- 地理索引、距离/围栏算法、地区内容池、审核和排序。它们是独立GeoOS系统服务，**不是可有可无的地图插件**；方向/可见/授权契约仍由K2执行。
- 业务清单训练、服务发现、方案生成、代码生成沙箱、工作流合成。
- Flutter组件、布局、渲染器、设备连接协议、ECM/OpenPorts实现细节。
- 支付、订单、社交、导航、广告等业务域实现。

这些服务必须向内核注册身份、能力与证据契约，不能因“外置”而绕过审计、隔离和方向边界。生物运行时、GeoOS关系服务、情境与呈现管理属于首批必备系统服务，不是装不装都不影响产品的可选插件；否则剩下的只是通用权限任务框架，而不是这个系统。

## 6. 地理主体不能统一成全能生物

| Geo角色 | 固定/移动 | 地理接收/感知 | 地理发布/发送 |
|---|---|---|---|
| Geomotion | 移动 | 有 | 有 |
| AReality | 固定 | 有 | 有 |
| Broadcast | 固定 | 无 | 有 |
| 地理群 | 以原BP的空间群语义为准，不在内核擅加移动权限 | 有 | 无 |

以上是**地理通信方向**，不是“是否具备麦克风”“是否能回应其所有者”“是否可读订单API”。为只广播主体增加语言表达能力，不应顺带给它感知周围主体的权限。每个主体可以绑定独立AIBM和Agent实现，但方向限制依旧生效。固定主体也不能因用户换位置就悄悄移动，移动主体的地理状态要有来源和可见范围。

区域政策由有明确权威的策略服务给出可验证版本；模型读到一段网页并不能把它变为地区规则。模拟区域可用于内核测试，但必须标记模拟，不能当成真实位置或合法广播权。

## 7. 三类入口与生成闭环

统一流程，不规定固定首页：

`用户呼唤 / 地理接触 / 业务事件 → 证据与情境 → 生物理解候选 → 需求/约束 → 找现有服务或生成候选 → 权限与政策核验 → 持续活动 → 真实回执 → 响应场景 → 新感知/纠正`

常用场景预生成是同一流程的准备阶段：在授权范围内读取已有偏好/日程/设备上下文，提出“工作”候选，生成本地/低风险呈现草案；并不等于替用户开展收费业务或主动向同事发布消息。打开App时可选当前可信情境的候选，首次无证据时让伙伴自然询问，不虚构用户正在上班。

每次场景生成至少说明 `forBeing / continuity / basisRevision / purpose / dataScopes / expiry`。来源过期、用户纠正或授权变化后，旧候选不能继续提交动作。系统仍需稳定可发现的隐私、停止和纠正控制，但这些系统控制不是固定业务首页。

## 8. 服务和界面“生成”的精确定义

设计目标不仅是模板换皮。需要支持从需求生成新的服务方案、交互结构与响应场景，持续随对话和环境改变。实现时区分三个阶段，不能混说：

1. **生成候选**：内容、布局或服务方案尚未验证，无业务执行权；调用模型生成本身可能外发数据或产生费用，必须先有相应数据用途和生成预算授权，“候选”不意味着免费或零副作用。
2. **装配与验证**：检查声明、输入/输出、效果、资源预算和能力依赖；生成内容不能增权。
3. **承载与执行**：用户/策略许可后，由受限服务执行器与渲染器承载，真实回执回到同一情境。

第一版内核只证明生成提案可安全装配已注册能力；这是边界试验，不代表已完成通用新代码生成。后续若生成新服务实现，必须进入独立沙箱、测试、签名清单与发布流程，不在内核直接eval模型代码。按需文本框也属于呈现方案，只有用户需求和当前输入权限支持时才能承载。

## 9. 最小接口草案

不是最终HTTP路由，先以类型化命令/事件固定语义：

- `registerBeing(manifest, principal)`：稳定身份、人格/关系命名空间与边界初版；不默认授予能力。
- `reviseBoundary(being, expectedVersion, change, authority)`：CAS更新/撤销，产生新世代。
- `bindRelation(relation, authority)`：受限关系及共享用途，不能用关系名替代授权。
- `admitEvidence(envelope, sourceLease)`：可信来源进入情境；不自动授权动作。
- `proposeActivity(continuity, serviceManifest, inputs, constraints, evidenceRefs)`：登记提案，不执行业务；若为生成提案而调用模型，那是另一个已授权活动。
- `authorizeAndSchedule(activity, grants, expectedRevisions, idempotencyKey)`：检查全边界后持久安排；真正dispatch时须再次通过同一权限门，不仅安排时检查。
- `reportExecution(activity, executorLease, receipt)`：保存执行器事实证据，处理重复/迟到/未知；事实入账与用户可见/后续执行授权分开，撤权后不将已发生事实删除。
- `bindPresentation(continuity, sceneManifest, targetLease, expectedRevision)`：承载/迁移/收起；不复制业务活动。

取消、暂停、恢复、查询是上述对象明确的状态操作。内核不提供“执行任意自然语言”的万能接口。

## 10. 第一颗微内核的验收，而不是第一批业务页面

先做纯契约内核及确定性适配器测试，不调用付费模型、真实广播或实际设备动作。通用性用跨场景证明，不用某一个聊天样例代替系统：

1. 同一用户有伙伴/工作两个生物，切模型/设备后ID、人格版本、私有关系和未完成活动保持，不能互读私有记忆。
2. 用户、地理、业务三个入口能进入同一情境，重复事件不重复活动；未经授权的其他所有者不能加入；经授权的用户替身与餐馆可以协作，但加入不获得全部历史或伙伴私有记忆。
3. 四个Geo角色在相同模拟世界中分别通过允许方向、拒绝禁止方向；给它LLM也不能改变结果。
4. 咖啡馆：未要求输入时无文本输入租约；明确要求后生成；收起/换端不结束群服务，取消权限立即失效。
5. 餐馆：看图→放大→跨端保持菜品/主体/订单提案身份；展示行为不下单；失败回执不能显示“已完成”。
6. 草编厂：外观生成与广播能力独立；遵守模拟地区版本与限频；离开场景/重启后持续任务仍可恢复且不会追赶爆发。
7. 空调：连接租约过期拒绝设备动作；只有用户授权的降级提醒才可安排，不能“已关机”。
8. 汽车：拒绝预约约束跨重启保留，接近事件仅触发允许的指导；不会因换场景丢失禁付费限制。
9. 工作情境：允许的情境证据预生成工作场景；用户纠正为休假后旧场景版本不能提交活动；不需要连续定位。
10. Agent/渲染/网络崩溃：取消与配额可执行，迟到结果不能越过撤权世代；外部不确定状态不伪造成功。

验收中传感器、模型、空间服务可明确使用确定性替身以证明内核边界；产品听觉/视觉/个性自然感必须另外用真实设备与真实模型验收，不能从这些契约测试推断。

## 11. 现有原型如何处理

保留，不推倒也不硬认成内核：

- 提取可复用的授权世代、所有者隔离、幂等/任务状态机/回执测试作为迁移基线。
- 现有JSON Kernel混合了业务、媒体记录、会话和模板，是实验实现；不直接重命名为微内核。
- Vosk/Tesseract、LLM适配器、Flutter、OpenPorts桥拆作内核外适配器；原有安全回归继续保留。
- 当前“固定口令→组件”及“语音→聊天会话”用于验证输运/边界，不能代表最终生成式伙伴体验。
- 在本设计完成来源核对、反例评审后，另起纯契约模块，先通过上述最小验收，再逐步接回真实适配器；不先迁移全部旧端点或开发更多业务页。

## 12. 尚需论证但不阻塞设计草案的事项

多设备离线如何仲裁同一情境版本；区域政策签发/撤销可信根；个人记忆的端云分层、删除和关联传播；真实动作执行器的幂等/核对接口；生成服务的沙箱和代码供应链；跨Agent协作的数据最小化与冲突；人格持续性如何由用户评估而非一句提示词保证。第一版不得把这些未知包装成既有能力。

## 14. 从实验中带入的失败证据

v0.17独立复核记录两项未解决限制，设计验收应覆盖而非继续加功能遮盖：

1. 语音对话没有端到端幂等调用ID，响应丢失后手动重发可能新增轮次；当前界面不自动重试。微内核的request identity应涵盖感知→活动→回应的因果链，同时区分“同一请求重试”和“用户真的说第二次”，不以内容文本相同来去重。
2. OpenPorts桥只做到实例级并发2，未实现按租户公平或跨进程预算。微内核资源契约需要明确预算归属、等待/拒绝策略、释放和恢复；单实例计数不能冒称分布式限流。

此外保留先前验证暴露的原则：被观察到的租约过期不能因墙钟回拨复活；取消后迟到结果不能扩大执行或披露，但已发生事实仍须受保护登记；JSON快照原子替换并非断电持久性；外部请求发出不等于业务完成；坏模型结构不能变成执行权限。第一版可以选择单进程可靠边界，但必须把这些保证和不保证写进契约。

## 15. 事实、授权、预测、呈现：一条完整时序

以“上班途中收到餐馆招呼”为例，所有地理/设备输入在首验中可标记模拟：

1. **事实/观察**：已获准的设备源报告位置/时间，地理服务报告有向可达关系；这只证明该源的观察。旁边音频不能证明用户要求下单，地理接近也不自动形成永久订阅。
2. **预测**：伙伴情境服务结合用户允许的习惯提出“可能要工作”“或许想吃午饭”。预测有证据版本、置信度与有效期，不改写用户明确意图。
3. **生成授权**：若生成场景需外发工作资料到模型，先核收件模型、数据用途和预算；未获准时只能使用本地允许信息或说明缺口，不先上传再问。
4. **呈现候选**：产生一个工作场景和可选餐馆提示，绑定情境版本；尚未下单。用户说“今天休假”时新版本替换预测场景，保留原有独立任务，但撤销依赖旧预测的活动许可。
5. **真实业务授权**：用户明确选择服务，餐馆获准加入当前订单情境，只能读取订单必要信息，不能读取个人伙伴关系/工作记忆。每条数据有自己的可见/用途范围，成员身份不是全量读取权。
6. **执行门**：活动排队后，在 `queued→running` 的授权门重新核验版本/连接/地区策略，记录一次执行许可和幂等身份，然后发给执行器。安排后撤权的请求不得进入门。这个本地门不是跨外部系统的原子事务，发出后仍可能有未知结果。
7. **事实回执**：若外部动作完成后网络断开、用户随后撤权，系统保留“已完成/待核实”的受保护事实，不抹成“没做过”，不自动重发。登记事实、使用结果、向用户/第三方披露分别判权。
8. **回应/迁移**：可显示时由呈现服务生成结果场景，手机离线则标明未交付；换屏不重复业务活动，语音响应丢失重试同一ID只恢复回执。用户真的发出第二次需求必须用新意图身份。

由这条时序得出的冻结前反例集：排队撤权；排队地区规则更新；电视声音/图像提示注入；生成前数据外发被拒；跨所有者最小共享；临时可达不自动成为营销关系；执行已完成但回执迟到；场景纠正而任务保留；重发不重复活动。只有这些语义稳定后才开始最小实现。
